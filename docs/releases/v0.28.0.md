# workbench v0.28.0

_2026-09-11_

Two headlines, both about state that was living in the wrong place.

**SSO logins survive a restart and a second instance.** The OIDC nonce was the
last piece of login state in a process-local `Map` while its `state` sat in the
database; it now rides in the same row.

**The browser live view stops needing a WebSocket, and starts saying which
replica it belongs to.** The portal's CDP view is now REST plus an SSE stream,
and every request that touches a browser session carries a per-user routing key
— so a multi-replica deployment can reach the one process that owns a user's
Chromium instead of getting there by luck.

Alongside those, plugin tools become callable over plain HTTP without an MCP
client, jot gating becomes a one-call change instead of a full redeploy, and the
landing site becomes the Pages root.

## New

- **Run any plugin tool over plain HTTP** (`POST /rest/:integration`). A
  non-agent caller — `curl`, a cron job, a Lambda, any language with no MCP SDK
  — had no way to run a tool without speaking JSON-RPC, and no way to get a
  result past 60,000 characters. That cap was never part of execution: it lives
  in the MCP renderer, applied while building content blocks. Everything under
  it — connection check, Zod validation and defaults, audit row, metrics, the
  bounded worker pool — is envelope-blind, so this is the *same* code path
  rather than a parallel one. `executeSingle`/`executeMany` are now exported
  from `mcp/meta-tools.ts` and `execute_tools` calls them; `api/rest-routes.ts`
  is envelope plus HTTP-status mapping and nothing else. Auth is the same
  `resolveMcpUser` that `/mcp` uses, so all three credentials work unchanged and
  the audit rows are indistinguishable — deliberately, since the credential and
  the user are what matter, not the framing. Both body shapes work:

  ```
  POST /rest/github  {"tool":"github_list_prs","args":{"owner":"acme"}}
  POST /rest/github  {"tool":"list_prs","owner":"acme"}
  ```

  `GET /rest` lists integrations and connection status; `GET /rest/:integration`
  lists that integration's tools with JSON Schemas. Full contract:
  [REST endpoint](../site/_content/reference/rest-endpoint.md). See also
  [the finding](../findings/2026-09-11-rest-tool-execution-endpoint.md) for why
  Fastify's exact-match content-type parsers beat regex ones, which is what made
  a bodyless `curl -X POST` work.
- **The CDP live view is REST + SSE, not a WebSocket.** Cookie capture and
  `browser_live_url` used to run over a raw CDP WebSocket proxy; they are now
  four plain endpoints per base path — `POST /attach`, `GET /events` (SSE),
  `POST /commands`, `POST /detach` — in `packages/server/src/auth/cdp-bridge.ts`.
  Chromium is unchanged and still only speaks CDP over a socket; that hop is
  entirely server-side. What went away is the socket between the browser and us,
  and with it the reason auth was ever an in-band frame: **a WebSocket cannot
  send an `Authorization` header**, so the client had to post its bearer as the
  first message while the server held an unauthorized socket open behind a 5s
  timeout and four bespoke close codes. `attach` is now a normal request that
  answers 401/403/201, and no chromium socket exists until it succeeds. A
  `channelId` is a handle, not a credential — every follow-up re-proves the
  portal session and must match the userId that opened it, so another user's
  channel reads as 404. Details:
  [CDP live view over SSE + REST](../findings/2026-09-10-cdp-live-view-over-sse-rest.md).
- **A browser session is routable across replicas** (`X-Browser-Session`).
  Everything about the per-user Chromium is process-local — the process itself,
  `warmSessions`, `activeProfiles`, the live-view channels — so every request
  touching it must reach the owning process. `attach` used to require a warm
  session and dial chromium, which was the worst possible arrangement: it is the
  only request with no key to route on, and it was the one committing a
  process-local resource. It now mints a key and starts nothing; the first
  `commands` POST starts chromium on whichever replica the key routed it to, and
  every later request follows the same hash. The key is
  `HMAC(SESSION_SECRET, userId)` and is **per user, not per attach** — two keys
  for one user hash to two replicas, both of which spawn on that user's single
  profile directory, and the second deletes the `SingletonLock` the first one's
  live browser holds. It is a routing hint, not a credential: every endpoint
  verifies the portal bearer first and resolves the session from the verified
  userId, never from the key. That also retires `cdpToken`, which since the
  2026-09-02 connect-link fix proved nothing the bearer did not already prove.
  Reasoning and the ingress config:
  [browser session pod affinity](../findings/2026-09-10-browser-session-pod-affinity.md).
- **Jot gating without a redeploy** (`update_jot`). Changing who can read a jot
  used to mean a full `deploy_jot`: re-tar and re-upload the whole tree just to
  set a password or make it public again. `update_jot` now takes `access`,
  `password` and `cors` directly and writes them to the live manifest at call
  time, echoing them back as `applied`. Settings inherit where unset — a
  `password` on its own implies access `password`, restating `password` without
  a new one keeps the current hash, and going public drops it.
  `store.updateJotMeta` rewrites only the manifest and stages the temp file
  outside the jot directory, so a half-written manifest is never servable.
- **Landing site at the Pages root** (`.github/workflows/pages.yml`). One
  deploy now publishes both: the landing site at `/`, the docs under `/docs/`.
  The Netlify build is gone — `netlify.toml` deleted, `README` and the docs
  topbar point at `barockok.github.io/workbench`. The Pages workflow also
  triggers on `site/`, `packages/brand/` and `packages/plugins/`, so a plugin
  added to the registry refreshes the integration counts on the landing page
  without a manual dispatch.
- **Contribution section.** The landing page shows what a plugin actually is —
  a `manifest.ts` and a `tools/index.ts` in a folder — and says the three things
  people ask before writing one: no fork needed, private to your instance until
  you open a PR, and the built-in integrations are written exactly the same way.
- **Teams section.** Four points on the multi-user story: one OAuth app per
  provider set up once on the instance, each person connecting their own
  account, one audit trail behind the Activity page, and revocation in one place.

## Fixes

- **The SSO nonce is persisted with its `pending_auth` row.** Google and
  Keycloak generated the OIDC nonce, kept it in a module-scope `Map` keyed by
  the auth state, and wrote the state to `pending_auth`. Half the login lived
  in memory and half in the database, so a restart between the redirect and the
  callback — or a callback load-balanced to a different instance — failed with
  `Invalid or expired nonce` while the state itself was still perfectly valid.
  The nonce now goes in a nullable `nonce` column on that same row: one
  lifetime, one `expires_at`, one single-use deletion (`verifyAuthState`
  already removed the row on lookup), and both `Map`s are gone. The fix is in
  the shared `createAuthState`/`verifyAuthState` helpers, so it covers Google
  and Keycloak identically rather than one provider at a time.
- **A live view with dead input now recovers instead of lying.** A 404 on
  `POST /commands` was swallowed: the SSE stream kept painting frames while
  every click and keystroke went nowhere — worse than an error, because it looks
  like it works. The client now treats `NO_CHANNEL` as "this channel is gone",
  cancels its stream and re-attaches, still bounded by `MAX_RECONNECTS`.
  Cancelling the reader explicitly rather than relying on the attempt's
  `AbortController` is deliberate: a body read already in progress does not
  observe a later abort in every runtime, and that is exactly the state the
  client is in here. A 401 *after* the view was live now reads "Session ended"
  rather than "Unauthorized" — after a reap those are the same status code with
  very different meanings.
- **Keycloak SSO has its own test file.** `packages/server/tests/keycloak-sso.test.ts`
  covers what only Google covered before — user creation, linking by email,
  unverified email — plus the three cases this change is about: the row is
  consumed so a replayed callback fails on state, a mismatched ID-token nonce is
  rejected, and a callback served after `vi.resetModules()` still succeeds,
  which is the multi-instance case in miniature.
- **The contribute section fits narrow viewports.** Its two-column grid did not
  collapse, so the code sample pushed the page wider than the screen on a phone.
- **Docs corrected on per-worker state.** `deploy/database.md` and
  `reference/environment.md` both listed the SSO nonce among the things held in
  process-local maps. Only the transient connect-flow records and the browser
  session are, now — SSO follows the database and needs no sticky routing.
- **Docs corrected on `/mcp` routing.** An earlier draft told operators to hash
  `/mcp` on `Authorization`, "which is equally per-user". It is not:
  `resolveMcpUser` takes identity from three carriers, and neither common one
  works as a hash key — an api-key agent sends no `Authorization` at all, so
  every such client hashes on an empty value and lands on one replica, and an
  OAuth Bearer rotates at its TTL, moving the hash under a live session. The
  honest position replaces it; see the upgrade note. Tracked in
  [#87](https://github.com/barockok/workbench/issues/87).
- **Docs site footer version.** `docs/site/nav.json` still read `0.24.0`, three
  releases stale, and the footer prints it verbatim.

## Upgrade note

**Schema change, applied automatically.** `ALTER TABLE pending_auth ADD COLUMN
nonce TEXT` runs at startup through the existing migration list on both SQLite
and Postgres. The column is nullable and only SSO writes it, so nothing else
in `pending_auth` is affected and there is no manual step.

SSO logins already in flight when you upgrade — redirected by the old build,
called back on the new one — fail once with `Invalid or expired nonce`, because
their nonce was in the old process's memory. Retrying the login works. The
window is the 10-minute `pending_auth` expiry.

### Proxy configuration changes

**You can drop the WebSocket forwarding rules.** Previous versions needed your
proxy to forward `Upgrade` for `/api/auth/cookie/:integration/cdp` and
`/api/browser-session/cdp`. Those routes are gone, and `@fastify/websocket` is
no longer a dependency. What replaces the instruction is narrower and more
common: **do not buffer or compress the SSE stream** (`.../cdp/events`). The
server sends `Cache-Control: no-transform` and `X-Accel-Buffering: no`, which
nginx honours; other proxies may need response buffering disabled explicitly.
Keep read timeouts above the stream's 15s keepalive. The `Origin` header must
still be preserved, and the allowlist is still exactly
`{PORTAL_URL, SERVER_PUBLIC_URL}`, compared verbatim — a trailing slash or an
explicit `:443` never matches and every attach 403s.

**Running more than one replica?** Hash `X-Browser-Session` to a pod on the
browser-session paths, or cookie capture and the live view fail intermittently:

```yaml
# nginx-ingress
nginx.ingress.kubernetes.io/upstream-hash-by: "$http_x_browser_session"
```

Three ways to silently lose that stickiness: hashing to a `Service` instead of
pod endpoints (a ClusterIP behind the hashing hop re-round-robins), modulo
instead of consistent hashing (`hash % N` remaps nearly every key when a pod
comes or goes, so one rollout breaks every live session), and `CLUSTER_ENABLED`
left on (it forks a worker per core, each with its own session map, and no
ingress can route inside a worker pool).

**`/mcp` is not covered by this.** An MCP client sends no such header, and
`Authorization` is not a usable substitute for the reasons in the fix above. So
if you use `browser_*` tools with more than one replica, pin them — and that
means pinning all `POST /mcp` traffic, since tool calls are not separable by
path. Tracked in [#87](https://github.com/barockok/workbench/issues/87).

### Jots

Two things to know about the new `update_jot` fields. Changing a jot's password
invalidates the unlock cookies already issued for it, because those are HMACs
over the hash — readers re-enter the password once. And **`cors` no longer
rides the patch token**: gating is read from the live manifest, never from the
token, so a patch archive on its own still cannot change who may read a jot.
If you were setting `cors` when minting a patch token, set it via `update_jot`
instead.

### Release candidate

Because this touches the database schema, the auth path and the proxy
configuration, it ships as `v0.28.0-rc.2` first and is promoted to `v0.28.0`
after a soak. Pull the RC explicitly — it is never tagged `latest`:

```
docker pull ghcr.io/barockok/workbench:v0.28.0-rc.2
```
