## v0.34.0: Spaces, live shareable pages that call tools as the viewer

Jots gave an agent somewhere to publish a finished page, but a jot is a
snapshot: whatever data the agent baked in at deploy time. Spaces are the live
version. An agent builds a page, and every time someone opens it the page calls
integration tools **as that person**, with their own connections. A "my open
PRs" timeline shows each viewer their own PRs; a Drive page lists and writes to
the viewer's own Drive. Spaces are shared privately, with the whole deployment,
or with a list of people, and the portal gains a gallery of the Spaces you can
open.

The hard part is trust. A Space's code is written by one user and runs with
another user's integrations, so it is treated as untrusted from end to end. See
[docs/findings/2026-11-07-spaces-bridge.md](../findings/2026-11-07-spaces-bridge.md)
for the reasoning behind each choice below, and the design spec in
`docs/superpowers/specs/2026-11-07-spaces-design.md`.

Ships as a release candidate first because it adds database tables and a new
authenticated API.

### Upgrade notes

- **Schema change, applied automatically at startup.** Four new tables,
  `spaces`, `space_shares`, `space_consents` and `space_kv`, on both SQLite and
  PostgreSQL. Nothing existing is altered.
- **Files on disk.** Space files live under `SPACES_DIR` (default `spaces/`
  next to the SQLite file). With several replicas, mount it on a shared volume,
  as you already must for `JOTS_DIR`, or a Space uploaded through one replica is
  a 404 on the others.
- **Re-copy the MCP config for Claude Code.** The portal's "Copy config" now
  includes `"type": "http"`. Without it, a config passed to Claude Code's
  `--mcp-config` loads no server at all, silently.

### Features

- **Spaces.** The agent calls `deploy_space` with a name, the tools the page may
  call and who can open it, then uploads a tarball, the same flow as
  `deploy_jot`. The page includes `/s/_sdk/workbench.js` and calls
  `workbench.call("github", "list_prs", {...})`. Also `update_space`,
  `list_spaces`, `list_space_files` and `delete_space`, and a small per-viewer
  key-value store (`workbench.store`) for things like remembered filters.
- **The page never holds a credential.** Author files are served sandboxed on
  an opaque origin with `connect-src 'none'` and no remote hosts. A trusted
  portal shell at `/s/<name>` owns the viewer's session and relays calls over a
  `MessageChannel` port to `POST /api/spaces/:name/call`. The viewer's portal
  session is never handed to the page: it can reach the vault, API keys and, for
  admins, `/api/admin`, which would make every other control advisory.
- **Consent and confirmation.** Each viewer approves a Space's tool list once.
  Any tool labelled `destructive` additionally needs a confirmation drawn by the
  shell on every call, which the author cannot turn off. Changing the tool list
  asks every viewer again.
- **Server-side limits on every call.** Only the Space's declared tools from
  external plugins (never `browser`, `jots`, `files`, `vault` or `spaces`, never
  custom apps); `{{vault:...}}` references are refused and never resolved; 60
  calls a minute per viewer per Space; the portal API accepts the portal session
  only. Every call is audited under the viewer, with `client_name =
  space:<name>`, so the Activity page shows which Space acted.
- **Tool effect labels.** Every tool now declares `effect: read | write |
  destructive`, and an unlabelled tool counts as destructive. All built-in and
  internal tools are labelled, and a test keeps it that way. `search_tools`,
  `get_tool_schema` (also as MCP `readOnlyHint` / `destructiveHint`) and
  `GET /rest/:integration` expose the label. Updating or transitioning
  tasks and issues, approvals, CI triggers and Gmail label changes count as
  destructive because they can close items, unlock merges, run jobs or trash
  mail. Plugin authors: see "Label the side effect" in the plugin guide.

### Fixes

- **Portal: copied MCP config lacked `"type": "http"`.** Claude Code needs it
  for a URL server; without it the config loaded nothing and gave no error.

### Known limits

- A Space can still navigate its own frame to an outside URL and put data in
  that URL, and DNS prefetch is not governed by CSP. Spaces resist
  exfiltration but cannot fully prevent it; consent lists exactly what a Space
  can call, every call is audited, and admins can delete any Space.
- Consent covers the tool list, not the code: an author can update a Space's
  files under the consent viewers already gave. Binding consent to the
  uploaded content is the next planned change.
- The call rate limit is counted per process.
