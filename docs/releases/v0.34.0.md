## v0.34.0: Spaces, live shareable pages that call tools as the viewer

Jots gave an agent somewhere to publish a finished page, but a jot is a
snapshot: whatever data the agent baked in at deploy time. Spaces are the live
version. An agent builds a page, and every time someone opens it the page calls
integration tools **as that person**, with their own connections. A "my open
PRs" timeline shows each viewer their own PRs; a Drive page lists and writes to
the viewer's own Drive. Spaces are shared privately, with the whole deployment,
or with a list of people, and the portal gains a gallery of the Spaces you can
open.

The hard part is trust. A Space's code is written by one user and runs with
another user's integrations, so it is treated as untrusted from end to end. See
[docs/findings/2026-11-07-spaces-bridge.md](../findings/2026-11-07-spaces-bridge.md)
for the reasoning behind each choice below, and the design spec in
`docs/superpowers/specs/2026-11-07-spaces-design.md`.

This release also stops cutting large tool results in half. A result over the
60,000-character MCP cap now comes back as a temporary download URL the agent
fetches with `curl` and filters locally, so a long Confluence page or a big
search result can be read whole without filling the agent's context.

OAuth connections also hold up better under load. A token that dies before its
stated expiry is refreshed and the call retried once, parallel calls share a
single refresh instead of racing with the same refresh token, and a grant that
can no longer be refreshed is reported as "reconnect" instead of an upstream
error.

Ships as a release candidate first because it adds database tables, a new
authenticated API, changes the shape of oversized MCP results, and changes how
OAuth tokens are refreshed.

### Upgrade notes

- **Schema change, applied automatically at startup.** Four new tables,
  `spaces`, `space_shares`, `space_consents` and `space_kv`, on both SQLite and
  PostgreSQL. Nothing existing is altered.
- **Files on disk.** Space files live under `SPACES_DIR` (default `spaces/`
  next to the SQLite file). With several replicas, mount it on a shared volume,
  as you already must for `JOTS_DIR`, or a Space uploaded through one replica is
  a 404 on the others.
- **Oversized results are now a URL.** Agents need HTTP access to
  `SERVER_PUBLIC_URL` to fetch them (Claude Code has it). A client that cannot
  fetch still gets a 2,000-character preview. Overflow files count against the
  per-user workspace quota and follow `WORKSPACE_TTL_HOURS`.
- **Re-copy the MCP config for Claude Code.** The portal's "Copy config" now
  includes `"type": "http"`. Without it, a config passed to Claude Code's
  `--mcp-config` loads no server at all, silently.

### Features

- **Spaces.** The agent calls `deploy_space` with a name, the tools the page may
  call and who can open it, then uploads a tarball, the same flow as
  `deploy_jot`. The page includes `/s/_sdk/workbench.js` and calls
  `workbench.call("github", "list_prs", {...})`. Also `update_space`,
  `list_spaces`, `list_space_files` and `delete_space`, and a small per-viewer
  key-value store (`workbench.store`) for things like remembered filters.
- **The page never holds a credential.** Author files are served sandboxed on
  an opaque origin with `connect-src 'none'` and no remote hosts. A trusted
  portal shell at `/s/<name>` owns the viewer's session and relays calls over a
  `MessageChannel` port to `POST /api/spaces/:name/call`. The viewer's portal
  session is never handed to the page: it can reach the vault, API keys and, for
  admins, `/api/admin`, which would make every other control advisory.
- **Consent and confirmation.** Each viewer approves a Space's tool list once.
  Any tool labelled `destructive` additionally needs a confirmation drawn by the
  shell on every call, which the author cannot turn off. Changing the tool list
  asks every viewer again.
- **Server-side limits on every call.** Only the Space's declared tools from
  external plugins (never `browser`, `jots`, `files`, `vault` or `spaces`, never
  custom apps); `{{vault:...}}` references are refused and never resolved; 60
  calls a minute per viewer per Space; the portal API accepts the portal session
  only. Every call is audited under the viewer, with `client_name =
  space:<name>`, so the Activity page shows which Space acted.
- **Tool effect labels.** Every tool now declares `effect: read | write |
  destructive`, and an unlabelled tool counts as destructive. All built-in and
  internal tools are labelled, and a test keeps it that way. `search_tools`,
  `get_tool_schema` (also as MCP `readOnlyHint` / `destructiveHint`) and
  `GET /rest/:integration` expose the label. Updating or transitioning
  tasks and issues, approvals, CI triggers and Gmail label changes count as
  destructive because they can close items, unlock merges, run jobs or trash
  mail. Plugin authors: see "Label the side effect" in the plugin guide.

- **Oversized MCP results go to a download URL instead of being truncated.**
  Past 60,000 characters, the full JSON is written to the caller's file
  workspace and the result becomes a small stub: `url`, `bytes`,
  `url_expires_at`, a preview, and a hint to `curl` it and filter with `jq`.
  The URL needs no auth header, can be fetched more than once, and expires after
  `WORKSPACE_PRESIGN_TTL_SECONDS` (300 by default). It reuses the workspace
  presign, so it works across replicas with no new storage, which is what
  sank the earlier chunk-and-continue attempt (#46). In an `execute_tools`
  batch only the largest items are swapped for stubs, one file each;
  `compose` chains still pass full results between steps because the cap
  applies only to the final reply. If the workspace refuses the write (file
  size or quota) the old truncation applies. See
  [docs/findings/2026-11-23-mcp-result-overflow-url.md](../findings/2026-11-23-mcp-result-overflow-url.md).

- **Spaces: grant or revoke one person.** `update_space` takes `add_users` and
  `remove_users`, which change those emails and leave everyone else on the
  list. Before this, the only option was `users`, which replaces the whole list,
  and `list_spaces` did not show the list, so an agent asked to share a Space
  with one more person sent just that email and revoked everyone else. The
  change runs in one transaction with the owner check, so concurrent edits keep
  each other's change. `users` together with `add_users`/`remove_users` is
  refused (`CONFLICTING_USERS`), emptying a `users` Space is refused
  (`USERS_REQUIRED`), and `list_spaces` now returns `users`. The descriptions
  also say plainly that `users`, and redeploying with `deploy_space`, replace the
  list.
- **Spaces: sharing settings in the portal.** Owners no longer need an agent
  to change who can open a Space: open it, then **Menu > Sharing**. Choose
  **Only me**, **Everyone signed in** (anyone who can sign in to this
  workbench) or **Specific people**. Addresses typed or pasted with commas
  become pills, **Add** puts them on the list, and **Save** sends only who was
  added or removed, so it never overwrites the rest. Long lists scroll inside
  the dialog. Behind it is `PATCH /api/spaces/:name/sharing` (portal session,
  owner only), with the same rules as `update_space`. The gallery badge for
  these Spaces now reads "Everyone signed in", and the Space top bar shows the
  workbench mark before "Spaces", linking home.
- **OAuth: retry once on 401, one refresh at a time.** `ctx.http()` refreshes
  and re-sends once when the upstream answers 401 (OAuth grants with a refresh
  token, re-sendable body; a 403 is never retried). Tokens used to be refreshed
  only on their stated expiry, so one revoked and re-granted, or from a provider
  that sends no `expires_in`, failed until the user reconnected. Refreshes now
  run one at a time per user and integration across every pod (a lock row in
  `pending_auth`, not a held transaction), and each attempt reuses a token
  someone else already refreshed. A Space page or `execute_tools` batch firing
  several calls near expiry used to refresh once per call with the same refresh
  token, which providers that rotate refresh tokens (Atlassian, GitLab) reject,
  and some answer by revoking the grant. Applies to `/mcp`, `/rest` and Space
  calls. See
  [docs/findings/2026-11-23-oauth-refresh-on-401-and-single-flight.md](../findings/2026-11-23-oauth-refresh-on-401-and-single-flight.md).
- **Spaces: the consent screen checks your connections first.** A Space acts
  through the viewer's own connections, so opening one whose integrations you
  have not connected used to let you approve it and then fail on the first call.
  Approve now stays disabled until every integration the Space uses is
  connected. Each unconnected integration has a **Connect** button that opens in
  a new tab, and the screen re-checks when you come back to it. The server
  enforces the same rule: `POST /api/spaces/:name/consent` answers 409
  `INTEGRATION_NOT_CONNECTED`, naming what is missing. Tools that no longer
  exist are ignored for this check.
- **Asana: custom fields, sections, start dates and subtasks.** An agent asked
  to report on a roadmap could not see Status, Priority, the brief/PRD/design/TRD
  ETAs, team sections, start dates or the dated phase subtasks (Development, UAT,
  Release, GTM), because the Asana tools never requested them. `asana_get_task`
  and `asana_list_tasks` now return `start_on`, the section, and `custom_fields`
  as a flat `{ name: value }` map (empty fields left out). New
  `asana_list_subtasks` returns a task's subtasks with their dates, and
  `asana_list_sections` a project's sections; the list tools page with `offset`.
  Create and update accept start date, `section` and `customFields` by name, for
  example `{ "Status": "In Progress", "Release Date": "2026-12-15" }`. Names are
  resolved and validated before anything is written, match case-insensitively,
  and accept a field gid, which is required when two fields share a name. Asana
  error replies now throw instead of returning an empty task. Reads were checked
  against a live workspace; writes are covered by unit tests only. See
  [docs/findings/2026-11-26-asana-custom-fields-sections-subtasks.md](../findings/2026-11-26-asana-custom-fields-sections-subtasks.md).

### Fixes

- **Connect links: a fresh link no longer says "Link already used".** Links the
  agent minted were kept in a per-process map. With several workers or pods the
  portal's redeem usually landed on a different one than the mint, which
  answered `LINK_CONSUMED`, and `wait_for_connection` had the same split.
  Pending connections are now `pending_auth` rows, redeemed once by
  compare-and-swap, so every process sees them and they survive a restart. See
  [docs/findings/2026-11-26-connect-link-cross-worker.md](../findings/2026-11-26-connect-link-cross-worker.md).

- **OAuth: a dead grant is `NOT_CONNECTED`, not an upstream error.** An expired
  token with no refresh token, or a refresh the provider refused (400/401,
  `invalid_grant`), came back as a generic error, so a Space showed
  `UPSTREAM_ERROR` (502) and nobody was told to reconnect. It is now
  `NOT_CONNECTED` with a reconnect message (a Space's 409). A token endpoint
  outage (5xx, timeout) is still a plain error.

- **Portal: copied MCP config lacked `"type": "http"`.** Claude Code needs it
  for a URL server; without it the config loaded nothing and gave no error.

### Known limits

- A Space can still navigate its own frame to an outside URL and put data in
  that URL, and DNS prefetch is not governed by CSP. Spaces resist
  exfiltration but cannot fully prevent it; consent lists exactly what a Space
  can call, every call is audited, and admins can delete any Space.
- Consent covers the tool list, not the code: an author can update a Space's
  files under the consent viewers already gave. Binding consent to the
  uploaded content is the next planned change.
- The call rate limit is counted per process.
