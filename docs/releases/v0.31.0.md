## v0.31.0 — an admin page, agents in browser calls, composed tool chains, and header-auth custom apps

Until now the only way to see what a workbench instance was doing was to read the database. This release adds an **Admin** page for the people who run it: instance health, every user's activity, who is connected to what, and the controls to disable a user, hide an integration, or stop people adding custom apps. It is gated by an email allowlist and is invisible to everyone else.

Since rc.1 three more things landed. An agent can now **join a browser-based call** (Zoom web client, Slack huddle, Google Meet) in its workbench browser, hear it as a raw audio stream and speak into it. `execute_tools` can **compose** a chain of tools server-side so large intermediate payloads never round-trip through the chat. And **custom MCP apps can authenticate with static headers** (API keys) instead of only OAuth.

Ships as a release candidate first: it touches auth (a disabled user is now refused at every credential check; header credentials for custom apps), adds columns and a table, adds a streaming proxy path, and changes the Docker image (PulseAudio).
### Features

- **Admin: the page and its gate.** Set `ADMIN_EMAILS` to a comma-separated list of emails. A signed-in user on that list gets an **Admin** link in the sidebar; everyone else gets a 403 from `/api/admin/*` and no link. The gate accepts the **portal session only**, never an API key or an OAuth bearer, so an admin's agent cannot act as the admin. Empty or unset means no admins and no admin page. See [the finding](../findings/2026-10-01-admin-gate-session-only.md) and the [admin guide](../site/_content/deploy/admin.md).
- **Admin: routed tabs.** Overview, Activity, Connections, Custom apps, Browser profiles, Vault, Files, Users and Config each have their own URL (`/admin`, `/admin/activity`, …), so the browser's back button works. A tab loads only when opened, so nothing walks the profiles or the workspace on disk until you ask.
- **Admin: Overview.** Headline numbers (tool calls and error rate over 24 hours with the change against the day before, users active in 7 days, connections that need a reconnect, disabled users), the most-called tools over 7 days, the last five failed calls, and the instance summary: version, database backend, cluster mode, audit destination, user and admin counts. Usage figures need `AUDIT_LOG_DEST=sqlite`; with stdout or kafka they show a dash and say why instead of reading as zero.
- **Admin: Activity.** Every user's tool calls, newest first, with email. Filter by app, errors only, or user email (search as you type). Tool names and error text only, never arguments.
- **Admin: Connections, Custom apps, Browser profiles.** Connected users per integration (with a derived "needs reconnect"), every custom app with its owner and URL, and browser-profile disk use per user. Credentials are never shown. See [the finding](../findings/2026-10-01-admin-overview.md).
- **Admin: Vault and Files.** Aggregates only. Vault shows secrets stored, users holding any, secrets unused for 90 days, pending one-time links and the top holders; Files shows disk used, file count, the age of the oldest file (older than `WORKSPACE_TTL_HOURS` means the reaper is not running) and the largest users and files. A secret's name is information too, so no name, value, file name or file content is ever returned.
- **Admin: disable a user.** The Users tab lists everyone with connection and custom-app counts, last activity and API-key state, and can **disable**, **enable** or **revoke the API key** of a user. You cannot disable yourself or any email on `ADMIN_EMAILS`. A disabled user is refused everywhere a credential is checked: API key, portal session, OAuth access token, curl-session token, both OAuth `/token` grants, and both SSO callbacks (the login page says "Your account has been disabled by an administrator"). Disabling also deletes the user's refresh tokens, so an existing client cannot mint a new access token. The check lives inside the verifiers, not at call sites, so a new entry point cannot forget it. See [the finding](../findings/2026-10-01-admin-users-config.md).
- **Admin: Config.** Turn an integration off for the whole instance and it disappears from every lookup (Apps, `search_tools`, `execute_tools`) at once, because the registry filters through one predicate. Set who may create custom apps (everyone, admins only, or no one); the Apps page hides **New custom app** when `/api/auth/me` reports `canCreateCustomApps: false`. Settings are an in-memory snapshot refreshed on write and by a poll, so other workers and pods lag by up to `INSTANCE_SETTINGS_POLL_SECONDS` (default 5).
- **Admin: every write is audited.** Disable, enable, revoke-key and both config changes write an audit row naming the acting admin.

- **Browser: agents in browser calls (behind `BROWSER_AUDIO_ENABLED`, default off).** `browser_audio_start { session_id, sample_rate? }` gives a tab a live audio pipe and returns a `stream_url`, a `clear_url` (capability URLs, below) and a routing header. `GET stream_url` is an SSE stream of the call audio as base64 PCM16 mono in 40 ms frames. One long chunked `POST stream_url` (`Content-Type: audio/pcm`) carries the agent's voice into the page's microphone, paced at real time server-side with a 120 s queue and backpressure. `POST clear_url` drops unplayed audio at once and returns `played_ms`, which maps onto a realtime voice API's `conversation.item.truncate` when the agent is interrupted. Workbench is only the pipe; speech recognition and voice come from the agent, and it is built for full-duplex realtime models. One call per user, bound to one tab. Mic permission is granted to one origin at a time and follows the meeting page across origin hops when joining. The browser is kept alive while a stream or uplink is attached and reaped as usual once the agent goes away. See the [browser audio guide](../site/_content/guides/browser-audio.md) and [the finding](../findings/2026-10-07-browser-audio-pipeline.md).
- **Browser audio: one PulseAudio daemon per user.** Each user's chromium is spawned onto a private virtual speaker and microphone. They are per *user*, not per server, because with a shared audio server chromium's `enumerateDevices()` lists every user's devices, and a page in one user's browser could record or inject another user's call.
- **Browser audio: capability URLs, no OAuth on the audio routes** (since rc.2). The client that holds a call open (a voice bot, say) is usually not the agent that started it and has no workbench token, so in rc.2 every audio request answered 401 and no call audio flowed. Each `browser_audio_start` now mints 128 random bits for that audio session and puts them in the path: `/api/browser/audio/<capability>/stream` and `/clear`, on the server's own origin. The capability is the only credential; an `Authorization` header is ignored, and an unknown or revoked one is a plain 404, never a redirect. It dies with the session: `browser_audio_stop`, `ended`, tab close, browser restart, `max_duration`, or 60 s with neither a reader nor an uplink attached (new end reason `idle`). A repeat start of a running session returns the same URLs. One reader and one uplink at a time: a second concurrent `GET` is now `409 stream_busy` instead of replacing the first (the `replaced` end reason is gone), and a reader whose socket stops draining for 10 s is dropped so a reconnect after a half-open TCP drop is not refused. The capability is masked in request logs and the paths get no trace spans. The result shape is fixed at `{ stream_url, clear_url, sample_rate, format, channels, session_id, restarted, headers }`, with no `stream_token`.
- **Browser audio: works across replicas.** The agent sends the returned `X-Browser-Session` header so the mesh routes it to the pod running its browser. A request that lands elsewhere is piped to the owning pod by the server itself over a streaming `node:http` forward (needs `INTERNAL_MCP_URL`). Since the capability names no user, that forward relays the caller's own `X-Browser-Session`, sends no credentials, and makes at most one hop.
- **MCP: compose tool chains in `execute_tools`.** With `compose: true`, executions run in order and each can read earlier results with `{{step:<ref_id>.path}}`, and `return` picks exactly which fields come back. A chain like *export a CSV → upload it to Drive* no longer moves the CSV body through the conversation (and into the 60k-token MCP result cap). Refs are checked before a step runs (`BAD_REF`), the chain stops at the first failing step and names it, and every step goes through the same auth, vault resolution, validation, audit and scrubbing as a normal call. `return` also works without `compose` to trim a parallel batch. MCP only for now.
- **Custom apps: static header auth.** A custom MCP app can authenticate with request headers (an API key, `X-Api-Key`, a custom `Authorization`) instead of OAuth. Add it with **Headers** in the portal or `authType: "headers"`. The server verifies it live against the app (`tools/list`, 15 s bound) before saving, so a wrong key returns 400 and nothing is stored. Header values are encrypted at rest and write-only: APIs return header names only, and values are redacted from call-time errors. Header apps show as connected immediately; there is no Connect/Disconnect. See the [custom apps guide](../site/_content/guides/custom-apps.md) and [the finding](../findings/2026-10-06-custom-app-header-auth.md).

### Fixes

- **Docker: the image reports its real version.** The image shipped no `package.json`, so every container reported `0.0.0`, on the admin Overview and to custom MCP servers. The Dockerfile now copies it and `readVersion` tries both the checkout and the image layout.
- **MCP: `search_tools` accepts `limit` as a numeric string.** Some clients send `"20"` rather than `20`; it is now coerced instead of rejected.

- **Browser: a stale chromium exit no longer tears down a newer session.** If a user's browser was closed and immediately restarted, the old process's exit handler could remove the new session from the registry. It now only cleans up its own session.
- **MCP: compose no longer leaks vault secrets to custom apps.** For a custom-app step, compose re-ran vault resolution over args already filled from earlier steps. Literal `{{vault:x}}` text that arrived inside an earlier step's *output* (a PR title, a CSV cell) was therefore substituted with the secret and sent to the remote MCP server. Vault refs now resolve once, against the agent's own template only. Step refs also follow own properties only, so `{{step:a.__proto__}}` is missing rather than resolving to something that was never in the result.

### Security

- **Browser audio forward pins its target to the internal service.** The first version built the upstream URL with `new URL(request.url, internal)`. An absolute-form request target (`POST http://other-host/... HTTP/1.1`) would have sent the forward, carrying the caller's bearer or API key, to that host. The target is now the internal origin plus path and query only, and a raw-request regression test covers it. This never shipped in a tag.
- **Browser audio capabilities stay out of the forward path, logs and metrics.** With the routes now unauthenticated, the forward's upstream path is built from the validated capability and a fixed leaf rather than the request target (`new URL` resolves `%2e%2e` as a dot segment, which would have let a caller relay to a non-audio path on the internal service), a capability of the wrong shape is a 404 before any lookup or forward, and a mistyped path under `/api/browser/audio/` is answered by the audio routes rather than the app's not-found handler, which logs the raw URL. Unmatched requests of any kind now get the metrics label `unmatched` instead of their URL. Neither shipped in a tag.
- **Browser audio isolates users at the audio-server level** (one daemon per user; see Features), keeps no standing mic grant (with a `Browser.resetPermissions` fallback if a revoke fails), and never logs audio content.

### Compatibility

- **Schema (additive, idempotent, SQLite and PostgreSQL):** `users.disabled_at INTEGER` and a new `instance_settings` table (`key`, `value`, `updated_at`, `updated_by`). Both are created on boot. Rolling back leaves them unused, and an older build simply ignores `disabled_at`, which means **a rollback re-enables every disabled user**.
- **New settings:** `ADMIN_EMAILS` (default empty: no admins) and `INSTANCE_SETTINGS_POLL_SECONDS` (default 5). The Overview usage cards, Activity and Top tools need `AUDIT_LOG_DEST=sqlite`, which is already the default.
- A user with no row in `users` is not treated as disabled, so existing API keys and sessions are unaffected until an admin disables someone.
- **Known limits.** The Users list is capped at 500 and search covers only what was loaded (the tab says so). Internal plugins (browser, jots, files, vault) appear in Config and can be turned off. `disabled_integrations` is one JSON list written read-modify-write, so two admins on different workers within one poll interval can lose an update; the write re-reads the stored list first, which narrows the window.

- **Schema (additive, idempotent):** `custom_apps.headers_enc` (BLOB on SQLite, BYTEA on PostgreSQL), created on boot. Existing OAuth apps load unchanged.
- **Docker image:** installs `pulseaudio` and `pulseaudio-utils`. Nothing starts unless `BROWSER_AUDIO_ENABLED=true`.
- **New settings:** `BROWSER_AUDIO_ENABLED` (default `false`) and `BROWSER_AUDIO_MAX_MINUTES` (default 180, max 1440; above a 120-minute client call cap so the client ends the call first).
- **Reverse proxy for browser audio.** The uplink is one request held open for a whole call. A proxy in front of `/api/browser/audio/*` must keep the path out of its access logs (it is a credential) and needs no body-size cap (nginx's default 1 MB cuts a 24 kHz call after about 22 s), request and response buffering off, HTTP/1.1, and read/send timeouts at least as long as the longest call. nginx and ingress-nginx settings are in the guide and `deploy/docker.md`.
- **Browser audio, not yet proven:** the real-audio test (`TEST_AUDIO=1`, Docker) was measured on an arm64 Mac only, where chromium's output had 10–300 ms gaps every few seconds; native Linux is not yet measured. Soak this RC on Linux with a real meeting before promoting.
- **Browser audio, known open in rc.3:** on Jitsi (meet.jit.si) the agent's microphone is not picked up by the prejoin page ("You need to enable microphone and camera access"), so other participants cannot hear the agent, and a joined tab was seen ending on Jitsi's post-hangup page (`close3.html`). Both are under investigation and block promotion.
- **Custom apps known limits:** the session cache is keyed by user + URL, so two header apps on the same URL replace each other's sessions (as OAuth apps already do).
