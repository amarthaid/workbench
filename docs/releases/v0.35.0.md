## v0.35.0: a Spaces gallery that adapts to you, per-tool approvals, a tidier Sharing dialog and a much more useful audit trail

Two screens that felt unfinished since delegated access shipped are reworked, Spaces get per-tool Always allow / Ask first, and the gallery and Admin area gain a detail modal, owner delete and a Spaces tab.

### Features

**Waiting room for new sign-ups.** With `REQUIRE_SIGNUP_APPROVAL` on, a person
whose account waits for an admin no longer lands on the login page with a text
error. They get a `/waiting` page with a three step progress view (signed in,
waiting for approval, active). It checks quietly in the background, and once an
admin approves it starts a normal sign-in on its own and continues to where they
were headed. A declined request replaces the waiting step with the declined
message and a Back to sign in button. Old `/login?error=account_pending` links
still work. The page is a centered card with a connected stepper over the login
background. See [the findings](../findings/2026-11-28-signup-waiting-room.md).

**Space cards and the detail dialog.** Who can open a Space and whether it is
delegated now show as small icons (lock, people, globe, key) with a tooltip, not
wide text badges. A tile has an Open icon at its bottom right that opens the
Space without the detail dialog. The owner edits the title and description right
in the detail dialog by clicking them (Enter or blur saves, Escape cancels), so
the separate Edit details dialog is gone. In the running Space's View tools panel,
changes to the Allow all switches are applied together with Apply or dropped with
Discard, instead of saving on every click.

**Apps order.** Connectable apps come first, then your custom apps, and the
built-in tools (browser, jots, files, vault, spaces) last, on the Apps page and
the Home tiles.

**Spaces gallery.** The Spaces page was one flat grid, the same for everybody,
though Spaces matter unequally to different people. It now orders itself around
you. A heart on a tile marks a favorite; favorites come first as large tiles
(six at most, the rest compact), then the last four Spaces you opened, then the
rest by update time. A Space someone shared in the last 14 days that you have
never opened carries **New**. Search, **Mine** and **Shared with me** narrow the
list, and each tile has a cover generated from the Space's name (not a
screenshot, which would show one viewer's private data to everyone).

The number beside the heart is how many people favorited the Space, among people
who can still open it; it is hidden when zero and on private Spaces, and never
says who. Owners also see how many other people opened it in the last 30 days:
for a Space open to everyone signed in, and for a shared one only from five
people up, because a smaller number on a short share list would say who. An open
is recorded when the portal shell mounts the Space, once per person, rather than
when its files are fetched, which cannot tell an open from a reload and never
rechecks access. Order never depends on popularity, so Spaces open to everyone do
not crowd out the ones a small team relies on.

Owners can edit without opening the Space: the three-dot menu on their tile has
**Edit details** (title and description) and **Sharing**, the same dialog as
inside the Space, and the audience badge on their own tile opens it too. Editing
the title, description or audience no longer counts as the Space being updated;
a new tool list, an upload or a deploy still does. A portal edit of the title or
description is replaced by the next `deploy_space`, which sets both by design.
See
[docs/findings/2026-11-27-space-gallery-favorites-and-opens.md](../findings/2026-11-27-space-gallery-favorites-and-opens.md).

**Sharing dialog.** "Delegate my access" moves to its own first tab, **Access**;
who can open the Space stays on a second tab, **People**. The tab labels carry
the state (On, Paused, Not saved; the people count, Only me or Everyone). Once
delegation is on, the dialog finally shows a status and the tools being lent,
grouped by app. The button reads **Review and delegate** whenever saving leads to
the confirm step. When an admin removes the delegate permission the tab strip
disappears and one line explains why, with a Turn off button.

**Activity (yours and the admin card).** A **Filters** button replaces a growing
row of controls. Date range and All / Errors stay on the bar; the popover holds
App, Space, Person (or User for admins), Credential and Delegated calls only, and
applies them in one request. Clicking a row opens a detail drawer with the full
error, the delegated-access details and the request origin; admins reveal the
arguments and result in the same drawer, still one audited click away. A
delegated call now names the other person right under the tool. The Space and
person boxes are searchable, and typing in them never queries the audit log.

**Always allow / Ask first.** Inside a Space, only destructive tools asked before running; writes ran silently, and nobody could change that. Every non-read tool now has a mode, set per tool, like a connector's tool settings: defaults are unchanged (write: Always allow, destructive: Ask first), read tools never ask. In an ordinary Space each viewer chooses on the consent screen and later in View tools, with an **Allow all** switch per app and one for the whole list. In a delegated Space the owner's own choices are the policy for every viewer: viewers only approve and see a read-only badge per tool, loosening a tool (Ask first to Always allow) asks each viewer to approve again, tightening applies at once. Modes can be set only in the portal: no MCP tool, API key or Space page can change one, and the server enforces the mode on every call (a write set to Ask first gets the same 428 a destructive call gets). Because Always allow removes the click that used to guard a page swap, anyone with an Always allow on a tool that defaults to Ask first approves again whenever the Space itself is updated (an upload or a new tool list); everyone else is not re-asked. See [docs/findings/2026-11-27-space-tool-approvals.md](../findings/2026-11-27-space-tool-approvals.md).

**Space detail and delete.** Clicking a Space card now opens a detail modal instead of the Space. The generated cover is its header, with the name and owner on it; under it are the likes, who opened it (owners only, same privacy rule as the tile) and when it was updated, then the full description. Tools show as totals by effect and one collapsible box per app; click a tool for its full description (rendered as markdown, with no raw HTML, no images and only http, https and mailto links) and what its effect means. **Open** goes to the Space. Owners get **Edit details**, **Edit sharing** and **Delete Space** there; the three-dot menu on tiles is gone. Deleting asks the owner to type the Space name and says who it affects, and cancels any open access requests for it. New `DELETE /api/spaces/:name` (portal session only) and a `SPACE_DELETE` audit row.

**Admin: Spaces tab and a custom apps permission.** A new **Spaces** tab lists every Space as a card (owner, audience, last updated, description, likes, how many people opened it in 30 days, expandable to who, capped at 50 per Space), paged and searchable. Who can add custom apps moves from an instance setting in Config to a per-user permission, **Add and use custom apps**, set in Admin Users next to the delegate permission, default deny. A denied user also stops seeing existing custom-app tools, as with the old "none" setting. See [docs/findings/2026-11-28-space-detail-and-admin-polish.md](../findings/2026-11-28-space-detail-and-admin-polish.md).

**Activity filters.** Picking a Space or User suggestion with the mouse no longer closes the filter popover (the clicked option was removed from the page before the outside-click check ran), and the popover has equal padding on all sides.

**One look across the portal.** The older pages now follow the Spaces design. Files, Vault and Agents are rich rows instead of tables, red-text actions and three confirm levels are used everywhere (an undo toast for things that expire or can be recovered, a simple confirm for revocable things, the typed name for irreversible ones), loading shows skeletons instead of zeros, and pages no longer shift sideways when a scrollbar appears. See [docs/findings/2026-11-28-ui-consistency.md](../findings/2026-11-28-ui-consistency.md).

- **Files:** the full machine name is cut in the middle so the timestamp survives, Download is always visible and Delete shows on hover and keyboard focus. Checkboxes give a bulk bar (download or delete several), and sort and a name filter appear above 15 files. A single delete has no dialog: it waits 5 seconds behind an undo toast, the row is hidden meanwhile, and closing the tab inside that window cancels the delete.
- **Vault:** each secret shows its `{{vault:name}}` reference as a click-to-copy chip (it copies the reference, never the value), and deleting asks for the secret name.
- **Agents:** each agent row shows its client id (two agents can share a name), with a visible Revoke that names the client id in its confirm.
- **Apps:** a tile opens a quick view (logo, connection state, version and tool count, and the tools grouped with effect badges and markdown descriptions), with a Manage link to the full page. `/apps/:name` is unchanged as a page, so connect links and deep links keep working. Removing a custom app (previously Delete app) asks for its name, and the "+" is now an "Add custom app" button.
- **Home, Settings, Admin:** Home shows skeletons while it loads, "Your apps" as tiles and a new "Your Spaces" row. Settings has a labeled Light and Dark control. Admin Users rows stay on one line, Admin Spaces cards get a cover band, the Space modal shows "Delegated", and the Activity filter shows a Space's title.

### Fixes and hardening

- If an admin removes the delegate permission and the owner then widens the
  audience, the stored delegation is turned off (and audited) instead of waking up
  unreviewed when the permission returns.
- On a call someone else made through your Space, their IP address and browser
  are no longer sent to you at all.
- A date range sent to the activity endpoints is capped at 90 days, and unknown
  filter values are refused.

**Maker-checker.** Two places where someone asks and someone else decides now
share one approval engine. New accounts: with `REQUIRE_SIGNUP_APPROVAL=true` a
first sign-in is held as pending until an admin approves it (Admin, Approvals).
Spaces: a person who is not on a Space's share list can ask the owner for access,
and the owner approves or rejects from the gallery or the Sharing dialog. Users now
carry a `status` (active, pending, disabled). See
[docs/findings/2026-11-27-maker-checker.md](../findings/2026-11-27-maker-checker.md).

### Operator notes

This release adds a table, `space_user_state` (favorites and when each person last opened a Space), and an index on it, on both SQLite and PostgreSQL, created at startup; nothing existing is altered. It also adds an index, `idx_audit_created`, on `audit_log (created_at, id)`.
It is created at startup on both SQLite and PostgreSQL; on a very large audit
table, creation takes a moment. New endpoints: `GET /api/admin/spaces/search`,
`GET /api/activity/people`, `PUT` and `DELETE /api/spaces/:name/favorite`,
`POST /api/spaces/:name/open` and `PATCH /api/spaces/:name`. See
[docs/findings/2026-11-26-sharing-tabs-and-audit-drawer.md](../findings/2026-11-26-sharing-tabs-and-audit-drawer.md)
and `docs/superpowers/specs/2026-11-26-sharing-tabs-and-audit-drawer-design.md`.

Maker-checker adds a table, `approval_requests`, and a `users.status` column (backfilled from `disabled_at`), on both SQLite and PostgreSQL, created at startup. Pending and disabled users also keep `disabled_at` set for this release, so a worker still on the previous version keeps blocking them; the column is dropped in a later release. New setting `REQUIRE_SIGNUP_APPROVAL` (default off): turn it on only after every instance runs this release, because an older instance would create the new account active. The server refuses to start with it on and `ADMIN_EMAILS` empty. New endpoints: `GET /api/approvals`, `POST /api/approvals`, `POST /api/approvals/:id/approve`, `POST /api/approvals/:id/reject`, `DELETE /api/approvals/:id`, and `GET|POST /api/admin/approvals`. Keycloak sign-in now requires a verified email.

Custom apps gain an operator setting, `CUSTOM_APP_ALLOWED_HOSTS` (comma-separated exact hostnames, no wildcards), for MCP servers that live on a private network. A listed host skips the private-address checks; every other private host stays blocked. A failed OAuth discovery now names which fetch failed instead of a generic message.

Tool approvals add a table, `space_tool_approvals`, and two columns on `space_consents` (`auto_tools`, `space_updated_at`), on both SQLite and PostgreSQL, created at startup; nothing existing is altered and no existing approval is invalidated. After plugins load, a one-time pass records today's defaults on existing delegated consents so a later change in a tool's effect is noticed. During a rolling deploy, a re-approval served by a pod still on the previous version keeps the previous approved set until that pod restarts. New endpoint: `PUT /api/spaces/:name/tool-approvals`.

The custom apps policy becomes a permission. On first start a one-time migration turns the old setting into per-user rows so nobody loses access: policy "all" (the default, also when nothing was ever set) allows every existing user, "allowlist" allows the listed users, "none" allows nobody. People who sign up afterwards start denied until an admin allows them in Admin Users. Existing custom apps are untouched, and the Config page no longer shows the setting. New endpoints: `GET /api/admin/spaces` now returns the Spaces list (cursor paged, `q` searches name and title), and `DELETE /api/spaces/:name` lets an owner delete a Space.

The app detail API, `GET /api/integrations/:name`, now returns each tool's `effect` (read, write or destructive) so the portal can label tools. No schema change in the UI release.
