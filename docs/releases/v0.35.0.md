## v0.35.0: a Spaces gallery that adapts to you, a tidier Sharing dialog and a much more useful audit trail

Two screens that felt unfinished since delegated access shipped are reworked.

### Features

**Spaces gallery.** The Spaces page was one flat grid, the same for everybody,
though Spaces matter unequally to different people. It now orders itself around
you. A heart on a tile marks a favorite; favorites come first as large tiles
(six at most, the rest compact), then the last four Spaces you opened, then the
rest by update time. A Space someone shared in the last 14 days that you have
never opened carries **New**. Search, **Mine** and **Shared with me** narrow the
list, and each tile has a cover generated from the Space's name (not a
screenshot, which would show one viewer's private data to everyone).

The number beside the heart is how many people favorited the Space, among people
who can still open it; it is hidden when zero and on private Spaces, and never
says who. Owners also see how many other people opened it in the last 30 days:
for a Space open to everyone signed in, and for a shared one only from five
people up, because a smaller number on a short share list would say who. An open
is recorded when the portal shell mounts the Space, once per person, rather than
when its files are fetched, which cannot tell an open from a reload and never
rechecks access. Order never depends on popularity, so Spaces open to everyone do
not crowd out the ones a small team relies on.

Owners can edit without opening the Space: the three-dot menu on their tile has
**Edit details** (title and description) and **Sharing**, the same dialog as
inside the Space, and the audience badge on their own tile opens it too. Editing
the title, description or audience no longer counts as the Space being updated;
a new tool list, an upload or a deploy still does. A portal edit of the title or
description is replaced by the next `deploy_space`, which sets both by design.
See
[docs/findings/2026-11-27-space-gallery-favorites-and-opens.md](../findings/2026-11-27-space-gallery-favorites-and-opens.md).

**Sharing dialog.** "Delegate my access" moves to its own first tab, **Access**;
who can open the Space stays on a second tab, **People**. The tab labels carry
the state (On, Paused, Not saved; the people count, Only me or Everyone). Once
delegation is on, the dialog finally shows a status and the tools being lent,
grouped by app. The button reads **Review and delegate** whenever saving leads to
the confirm step. When an admin removes the delegate permission the tab strip
disappears and one line explains why, with a Turn off button.

**Activity (yours and the admin card).** A **Filters** button replaces a growing
row of controls. Date range and All / Errors stay on the bar; the popover holds
App, Space, Person (or User for admins), Credential and Delegated calls only, and
applies them in one request. Clicking a row opens a detail drawer with the full
error, the delegated-access details and the request origin; admins reveal the
arguments and result in the same drawer, still one audited click away. A
delegated call now names the other person right under the tool. The Space and
person boxes are searchable, and typing in them never queries the audit log.

### Fixes and hardening

- If an admin removes the delegate permission and the owner then widens the
  audience, the stored delegation is turned off (and audited) instead of waking up
  unreviewed when the permission returns.
- On a call someone else made through your Space, their IP address and browser
  are no longer sent to you at all.
- A date range sent to the activity endpoints is capped at 90 days, and unknown
  filter values are refused.

**Maker-checker.** Two places where someone asks and someone else decides now
share one approval engine. New accounts: with `REQUIRE_SIGNUP_APPROVAL=true` a
first sign-in is held as pending until an admin approves it (Admin, Approvals).
Spaces: a person who is not on a Space's share list can ask the owner for access,
and the owner approves or rejects from the gallery or the Sharing dialog. Users now
carry a `status` (active, pending, disabled). See
[docs/findings/2026-11-27-maker-checker.md](../findings/2026-11-27-maker-checker.md).

### Operator notes

This release adds a table, `space_user_state` (favorites and when each person last opened a Space), and an index on it, on both SQLite and PostgreSQL, created at startup; nothing existing is altered. It also adds an index, `idx_audit_created`, on `audit_log (created_at, id)`.
It is created at startup on both SQLite and PostgreSQL; on a very large audit
table, creation takes a moment. New endpoints: `GET /api/admin/spaces`,
`GET /api/activity/people`, `PUT` and `DELETE /api/spaces/:name/favorite`,
`POST /api/spaces/:name/open` and `PATCH /api/spaces/:name`. See
[docs/findings/2026-11-26-sharing-tabs-and-audit-drawer.md](../findings/2026-11-26-sharing-tabs-and-audit-drawer.md)
and `docs/superpowers/specs/2026-11-26-sharing-tabs-and-audit-drawer-design.md`.

Maker-checker adds a table, `approval_requests`, and a `users.status` column (backfilled from `disabled_at`), on both SQLite and PostgreSQL, created at startup. Pending and disabled users also keep `disabled_at` set for this release, so a worker still on the previous version keeps blocking them; the column is dropped in a later release. New setting `REQUIRE_SIGNUP_APPROVAL` (default off): turn it on only after every instance runs this release, because an older instance would create the new account active. The server refuses to start with it on and `ADMIN_EMAILS` empty. New endpoints: `GET /api/approvals`, `POST /api/approvals`, `POST /api/approvals/:id/approve`, `POST /api/approvals/:id/reject`, `DELETE /api/approvals/:id`, and `GET|POST /api/admin/approvals`. Keycloak sign-in now requires a verified email.
